# FastAPI 后台管理系统 API 基座功能清单

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档用途 | 定义 FastAPI 后台管理系统 API 基座的功能范围、架构边界和交付标准 |
| 目标用户 | 中小型企业后台管理系统及其后续业务项目 |
| 系统形态 | 模块化单体应用 |
| 部署目标 | 单机部署，支持单机多进程 |
| 一致性核心 | PostgreSQL |
| 默认缓存 | 不依赖 Redis |
| 默认文件存储 | 本地文件系统 |
| 兼容策略 | 全新系统，不兼容旧代码、旧接口和旧数据 |

## 2. 建设目标

本基座作为后续后端项目的统一起点，应满足以下目标：

- [ ] 提供稳定、清晰、可复用的后台管理通用能力。
- [ ] 业务项目可以在不修改核心模块的前提下新增业务模块。
- [ ] 保持模块高内聚、低耦合和单一职责。
- [ ] 明确 API、应用服务、领域规则和基础设施之间的依赖方向。
- [ ] 支持单机环境下的开发、测试、部署、升级、备份和恢复。
- [ ] 不强制依赖 Redis、消息队列、对象存储和 Kubernetes。
- [ ] 为确有需求的基础设施替换保留清晰边界，但不提前实现复杂能力。
- [ ] 代码结构、命名、依赖和状态流应易于开发者及 AI 理解和推导。

## 3. 非建设目标

以下能力不进入基座核心范围：

- [ ] 不建设微服务体系。
- [ ] 不建设服务注册、服务发现和配置中心。
- [ ] 不建设分布式事务。
- [ ] 不建设分布式锁。
- [ ] 不建设强制性的分布式缓存。
- [ ] 不建设消息队列和死信队列平台。
- [ ] 不建设 Kubernetes 专用部署体系。
- [ ] 不内置复杂审批流和通用工作流引擎。
- [ ] 不内置报表设计器、低代码平台和表单设计器。
- [ ] 不内置支付、订单、库存等具体业务功能。
- [ ] 不保留 legacy、deprecated、灰度或 fallback 逻辑。
- [ ] 不为了未来可能发生的需求提前创建无实际用途的抽象层。

## 4. 功能分级

| 等级 | 含义 |
| --- | --- |
| P0 | 基座首个可用版本必须完成 |
| P1 | 建议在正式复用前完成 |
| P2 | 根据具体项目按需启用 |
| 排除 | 不属于当前基座范围 |

## 5. 总体架构

### 5.1 模块化单体

- [ ] 应用以一个代码仓库和一个主要部署单元为基础。
- [ ] 系统按照业务能力划分模块，而不是仅按照技术文件类型划分目录。
- [ ] 用户、认证、授权、组织、菜单、配置、字典、审计、文件等模块彼此独立。
- [ ] 每个模块独立维护路由、应用服务、领域模型、数据模型和测试。
- [ ] 跨模块调用只能通过公开的应用服务或明确的接口完成。
- [ ] 禁止跨模块直接操作对方的数据表、ORM 模型和内部函数。
- [ ] 禁止路由层直接访问数据库。
- [ ] 禁止基础设施层反向依赖 API 层或应用层的具体实现。
- [ ] 禁止通过全局变量保存关键业务状态。
- [ ] 公共代码只承载稳定、无业务归属的能力，禁止形成无边界的 `utils` 模块。

### 5.2 推荐依赖方向

```text
HTTP 请求
    ↓
API / Router / Request Schema
    ↓
Application Service / Use Case
    ↓
Domain Policy / Domain Service
    ↓
Repository Interface / Infrastructure Port
    ↓
PostgreSQL / File System / External Service
```

依赖规则：

- [ ] 外层可以依赖内层定义的接口。
- [ ] 内层不得依赖外层实现。
- [ ] 领域规则不得依赖 FastAPI、ORM、HTTP 或具体存储 SDK。
- [ ] 事务边界由应用服务控制。
- [ ] DTO、API Schema、领域对象和 ORM 模型职责分离。
- [ ] 不强制为纯 CRUD 模块创建没有实际领域逻辑的复杂领域模型。

### 5.3 单机部署拓扑

```text
客户端
  ↓
Nginx / Caddy
  ↓
FastAPI API（一个或多个 Worker）
  ↓
PostgreSQL

可选进程：
- Scheduler：产生定时任务
- Worker：执行持久化后台任务

本地资源：
- 文件存储目录
- 应用日志目录或标准输出
- 数据库及文件备份目录
```

- [ ] API 服务保持无状态，支持在同一台服务器启动多个 Worker。
- [ ] 多 Worker 不共享 Python 进程内状态。
- [ ] 定时调度器不得在每个 API Worker 内重复启动。
- [ ] 关键后台任务不得只存在于进程内存中。

## 6. 应用启动与系统基础能力

### 6.1 应用生命周期（P0）

- [ ] 提供统一的应用创建入口。
- [ ] 提供启动和关闭生命周期管理。
- [ ] 启动时校验必需配置。
- [ ] 启动时检查数据库连接。
- [ ] 关闭时释放数据库连接池和其他资源。
- [ ] 禁止在模块导入阶段执行数据库访问等隐式副作用。
- [ ] 支持开发、测试和生产环境配置。
- [ ] 提供应用名称、版本、环境等运行信息。

### 6.2 健康检查（P0）

- [ ] 提供存活检查接口。
- [ ] 提供就绪检查接口。
- [ ] 就绪检查能够验证数据库可用性。
- [ ] 健康检查返回内容不泄露敏感配置。
- [ ] 允许反向代理和进程管理器使用健康检查判断服务状态。

### 6.3 时间与时区（P0）

- [ ] 数据库存储统一使用 UTC。
- [ ] API 时间字段统一使用带时区的 ISO 8601 格式。
- [ ] 展示时区由调用端或明确的系统配置决定。
- [ ] 禁止使用无时区语义的时间参与关键业务计算。

## 7. 配置管理

### 7.1 部署配置（P0）

- [ ] 通过环境变量或受控配置文件加载部署配置。
- [ ] 提供开发环境配置示例，但不提交真实密钥。
- [ ] 必需配置缺失时快速失败并给出明确错误。
- [ ] 配置项具有类型校验。
- [ ] 配置项具有清晰的名称、默认值和用途说明。
- [ ] 数据库地址、密钥、文件目录等部署配置不得存入系统配置表。
- [ ] 生产环境禁止使用不安全的默认密钥。

### 7.2 配置分类（P0）

- [ ] 明确区分部署配置、系统配置和业务配置。
- [ ] 部署配置由运维环境管理。
- [ ] 系统配置由后台管理员管理。
- [ ] 业务配置归属于具体业务模块。
- [ ] 禁止把三类配置混合到同一个无边界配置模块中。

## 8. 数据库基础设施

### 8.1 PostgreSQL 数据访问（P0）

- [ ] 提供数据库连接池。
- [ ] 支持异步数据访问。
- [ ] 提供请求级数据库会话。
- [ ] 提供统一的事务管理机制。
- [ ] 正确处理提交、回滚和连接释放。
- [ ] 数据库异常转换为稳定的应用异常。
- [ ] 避免在请求生命周期之外复用数据库会话。
- [ ] 避免 N+1 查询。
- [ ] 关键列表查询具有明确索引设计。

### 8.2 数据库迁移（P0）

- [ ] 使用数据库迁移工具管理结构变更。
- [ ] 所有表结构变更必须通过迁移文件交付。
- [ ] 迁移文件纳入版本控制。
- [ ] 部署前可以独立执行迁移。
- [ ] 迁移失败时不得继续启动新版本应用。
- [ ] 提供全新数据库初始化流程。
- [ ] 不提供旧系统数据兼容迁移和双写逻辑。

### 8.3 数据建模规范（P0）

- [ ] 每张业务表具有明确主键。
- [ ] 表名、字段名、索引名和约束名遵循统一规范。
- [ ] 外键关系是否使用数据库约束必须形成统一决策。
- [ ] 唯一性规则优先由数据库唯一约束保证。
- [ ] 金额、比例和精度数据禁止使用浮点类型。
- [ ] 枚举值具有稳定编码。
- [ ] 敏感字段明确加密、哈希或脱敏策略。
- [ ] 不把软删除设计成所有表的强制基类能力。
- [ ] 是否允许软删除由具体模块的数据生命周期决定。
- [ ] 审计日志等不可变数据不得通过通用 CRUD 随意修改。

### 8.4 并发与幂等（P0）

- [ ] 关键并发更新使用数据库事务、行锁或乐观锁处理。
- [ ] 幂等性优先使用业务唯一键和数据库唯一约束实现。
- [ ] 不依赖进程内锁保证跨 Worker 正确性。
- [ ] 不引入分布式锁。
- [ ] 冲突错误具有明确的业务错误码。

### 8.5 初始化数据（P0）

- [ ] 提供初始化管理员的安全命令。
- [ ] 提供基础权限点初始化机制。
- [ ] 提供基础菜单和系统字典初始化机制。
- [ ] 初始化过程可重复执行且不会创建重复数据。
- [ ] 初始化密码不得硬编码到仓库。
- [ ] 开发演示数据和生产初始化数据相互分离。

## 9. API 通用规范

### 9.1 路由与版本（P0）

- [ ] API 使用统一前缀。
- [ ] API 具有明确版本，例如 `/api/v1`。
- [ ] 路由按业务模块分组。
- [ ] 路由命名与 HTTP 方法语义一致。
- [ ] 禁止通过一个巨型路由文件承载全部接口。
- [ ] 不为不存在的旧客户端保留兼容路由。

### 9.2 请求模型（P0）

- [ ] 请求参数使用明确的 Schema 校验。
- [ ] 创建、更新、查询和响应模型按职责区分。
- [ ] 更新接口明确区分全量更新和部分更新。
- [ ] 字符串长度、数值范围、格式和枚举具有约束。
- [ ] 未知字段的处理策略保持统一。
- [ ] 文件上传具有大小、类型和数量限制。

### 9.3 响应模型（P0）

- [ ] 成功响应格式保持一致。
- [ ] 错误响应格式保持一致。
- [ ] 统一响应结构不得破坏 HTTP 状态码语义。
- [ ] 响应字段具有稳定命名规范。
- [ ] 敏感字段不得进入响应模型。
- [ ] API 文档准确展示实际响应结构。

### 9.4 分页、排序和筛选（P0）

- [ ] 提供统一分页参数。
- [ ] 分页响应包含总数、页码、每页数量和数据列表。
- [ ] 对每页最大数量进行限制。
- [ ] 排序字段使用白名单。
- [ ] 筛选字段由具体模块显式声明。
- [ ] 禁止将客户端输入直接拼接为 SQL。
- [ ] 大数据量场景可按模块采用游标分页，但不强制所有模块使用。

### 9.5 请求上下文（P0）

- [ ] 每个请求生成或接收唯一 Request ID。
- [ ] 请求上下文包含当前用户、当前会话和必要的安全信息。
- [ ] 请求上下文显式传递，不依赖难以推导的隐式全局状态。
- [ ] Request ID 写入响应头和结构化日志。

### 9.6 OpenAPI 文档（P0）

- [ ] 接口按模块分组。
- [ ] 每个接口具有摘要和必要说明。
- [ ] 请求、响应和错误模型完整。
- [ ] 认证方式正确集成到 OpenAPI。
- [ ] 生产环境可以关闭文档或限制访问。
- [ ] 文档不暴露内部密钥、数据库信息和堆栈详情。

## 10. 异常与错误码

### 10.1 异常体系（P0）

- [ ] 区分参数错误、认证错误、授权错误、资源不存在、状态冲突和系统错误。
- [ ] 领域错误与 HTTP 异常解耦。
- [ ] 在 API 边界统一完成异常到 HTTP 响应的转换。
- [ ] 未处理异常记录完整日志。
- [ ] 生产响应不得返回调用栈和内部实现细节。
- [ ] 数据库约束错误转换为可理解的应用错误。

### 10.2 错误码（P0）

- [ ] 错误码全局唯一且稳定。
- [ ] 错误码按模块划分命名空间。
- [ ] 错误码与展示文案分离。
- [ ] 每个错误码具有含义、HTTP 状态码和适用场景。
- [ ] 禁止以临时字符串作为长期业务判断依据。

## 11. 用户管理

### 11.1 用户生命周期（P0）

- [ ] 创建用户。
- [ ] 查询用户详情。
- [ ] 分页查询用户列表。
- [ ] 更新用户基本资料。
- [ ] 启用用户。
- [ ] 禁用用户。
- [ ] 重置用户密码。
- [ ] 用户修改自己的密码。
- [ ] 用户查询自己的资料。
- [ ] 用户更新允许自助修改的资料。
- [ ] 查看用户关联的角色、部门和岗位。
- [ ] 禁止普通管理员越权修改高权限用户。
- [ ] 禁止删除或禁用系统唯一可用的超级管理员。

### 11.2 用户字段（P0）

- [ ] 用户名或登录账号。
- [ ] 显示名称。
- [ ] 密码哈希。
- [ ] 用户状态。
- [ ] 手机号和邮箱按项目需要启用。
- [ ] 最近登录时间。
- [ ] 密码更新时间。
- [ ] 创建时间和更新时间。
- [ ] 创建人和更新人按审计需要记录。

### 11.3 用户删除策略（P0）

- [ ] 明确用户注销、禁用和删除之间的语义。
- [ ] 已产生审计记录的用户不得因物理删除导致审计信息失真。
- [ ] 默认优先采用禁用或注销，而不是直接删除用户。
- [ ] 用户名称发生变化时，历史审计记录仍能识别当时操作者。

## 12. 认证与会话

### 12.1 账号密码认证（P0）

- [ ] 用户名和密码登录。
- [ ] 密码使用安全的单向哈希算法。
- [ ] 登录前检查用户状态。
- [ ] 登录成功创建服务端会话。
- [ ] 登录失败记录安全事件。
- [ ] 返回短期 Access Token。
- [ ] 返回或安全传递 Refresh Token。
- [ ] Token 中只携带必要且稳定的信息。
- [ ] 不在 Token 中放置敏感资料。

### 12.2 Token 刷新（P0）

- [ ] 使用 Refresh Token 获取新的 Access Token。
- [ ] Refresh Token 只保存不可逆摘要。
- [ ] 支持 Refresh Token 轮换。
- [ ] 检测已使用、已过期和已吊销的 Refresh Token。
- [ ] 刷新时检查用户和会话状态。
- [ ] 会话被吊销后不可继续刷新。

### 12.3 会话管理（P0）

- [ ] 会话信息持久化到 PostgreSQL。
- [ ] 用户可以查看自己的活动会话。
- [ ] 用户可以退出当前会话。
- [ ] 用户可以退出其他会话。
- [ ] 管理员可以强制用户下线。
- [ ] 用户被禁用后，其有效会话全部失效。
- [ ] 用户重置密码后，可以按安全策略失效已有会话。
- [ ] 会话记录设备、IP、User-Agent、创建时间和最近活动时间。
- [ ] 会话具有绝对过期时间和必要的空闲过期策略。

### 12.4 登录安全（P0）

- [ ] 记录连续登录失败。
- [ ] 达到阈值后临时限制登录。
- [ ] 登录成功后按策略清理失败状态。
- [ ] 防止通过错误响应枚举有效用户。
- [ ] 登录和刷新接口具有请求频率限制。
- [ ] 登录日志记录成功、失败和失败原因分类。
- [ ] 不在日志中记录明文密码、完整 Token 和验证码。

### 12.5 可选认证能力（P2）

- [ ] 多因素认证。
- [ ] 邮箱验证码登录。
- [ ] 手机验证码登录。
- [ ] OAuth 2.0 登录。
- [ ] OpenID Connect 企业身份源。
- [ ] API Key。
- [ ] 服务账号。

## 13. 权限管理

### 13.1 RBAC 模型（P0）

- [ ] 用户。
- [ ] 角色。
- [ ] 权限点。
- [ ] 用户与角色关系。
- [ ] 角色与权限点关系。
- [ ] 权限点使用稳定编码。
- [ ] 权限点表达资源和操作，例如 `system:user:read`。
- [ ] 权限校验在服务端执行。
- [ ] 权限规则不依赖前端隐藏按钮实现安全控制。

### 13.2 角色管理（P0）

- [ ] 创建角色。
- [ ] 查询角色详情。
- [ ] 分页查询角色列表。
- [ ] 更新角色。
- [ ] 启用和禁用角色。
- [ ] 为角色分配权限点。
- [ ] 为角色分配菜单。
- [ ] 查询角色成员。
- [ ] 为用户分配角色。
- [ ] 移除用户角色。
- [ ] 系统内置角色具有明确保护规则。
- [ ] 禁止普通管理员给自己授予超出自身范围的权限。

### 13.3 权限校验（P0）

- [ ] 提供统一的认证依赖。
- [ ] 提供统一的权限校验入口。
- [ ] 路由层声明访问所需权限。
- [ ] 应用服务对关键操作执行必要的二次授权校验。
- [ ] 禁止各模块复制权限判断逻辑。
- [ ] 权限拒绝行为统一返回稳定错误码。
- [ ] 权限变更后按照明确策略使相关会话重新获取权限。

### 13.4 超级管理员（P0）

- [ ] 超级管理员能力具有显式定义。
- [ ] 超级管理员绕过规则集中管理。
- [ ] 禁止通过魔法用户 ID 判断超级管理员。
- [ ] 超级管理员关键操作记录审计日志。
- [ ] 防止系统失去最后一个可用超级管理员。

### 13.5 数据权限（P2）

- [ ] 数据权限作为独立授权策略实现。
- [ ] 支持本人、本部门、本部门及下级部门、指定部门和全部数据等范围。
- [ ] 数据权限与菜单权限、操作权限分离。
- [ ] 查询和修改操作均执行数据权限校验。
- [ ] 不通过在所有查询中复制粘贴条件实现数据权限。

## 14. 组织架构

### 14.1 部门管理（P1）

- [ ] 创建部门。
- [ ] 查询部门树。

## 23. 安全基线

### 23.1 HTTP 安全（P0）

- [ ] 生产环境通过 HTTPS 提供服务。
- [ ] 正确处理可信反向代理头。
- [ ] 配置可信 Host。
- [ ] CORS 使用明确来源白名单。
- [ ] 不允许生产环境无条件开放所有跨域来源。
- [ ] 设置必要的安全响应头。
- [ ] 限制请求体大小。
- [ ] 对上传接口使用更严格限制。

### 23.2 密码与密钥（P0）

- [ ] 密码使用适合密码存储的哈希算法。
- [ ] 每个密码具有独立随机盐。
- [ ] 密码策略可配置但具有安全下限。
- [ ] 禁止记录和回显密码。
- [ ] JWT 或其他签名密钥来自部署配置。
- [ ] 密钥不得提交到版本控制。
- [ ] 敏感配置的加密密钥与密文分离管理。

### 23.3 输入与输出安全（P0）

- [ ] 所有外部输入经过类型和范围校验。
- [ ] 数据库访问使用参数化查询。
- [ ] 富文本场景具有独立的内容安全策略。
- [ ] 日志内容防止换行注入。
- [ ] 响应中不泄露内部路径、SQL、配置和调用栈。
- [ ] 导出内容防范表格公式注入。

### 23.4 请求频率限制（P0）

- [ ] 登录、刷新 Token、找回密码等敏感接口必须限流。
- [ ] 单机默认优先由 Nginx 或 Caddy 执行入口限流。
- [ ] 若应用内实现限流，必须明确其在多 Worker 下仅为进程级限制。
- [ ] 不因限流需求强制引入 Redis。

### 23.5 权限安全（P0）

- [ ] 默认拒绝未认证访问。
- [ ] 公共接口必须显式声明。
- [ ] 所有管理接口具有权限点。
- [ ] 批量接口逐项或按集合执行授权校验。
- [ ] 资源 ID 不构成访问授权。
- [ ] 禁止仅依赖前端菜单和按钮控制权限。

- [ ] 扩展失败不得破坏核心事务，除非业务明确要求强一致性。

## 32. 明确不采用的实现方式

- [ ] 不使用一个通用 Service 承载所有模块业务。
- [ ] 不使用一个万能 Repository 表达全部查询。
- [ ] 不让 Router 直接提交数据库事务。
- [ ] 不把 ORM 模型直接作为所有 API 响应模型。
- [ ] 不把前端菜单当作服务端权限。
- [ ] 不通过魔法用户 ID 判断超级管理员。
- [ ] 不在每个查询中复制粘贴数据权限条件。
- [ ] 不使用进程内锁保证跨 Worker 的数据正确性。
- [ ] 不在每个 API Worker 中启动定时调度器。
- [ ] 不用 FastAPI 进程内后台任务执行不可丢失任务。
- [ ] 不把所有配置放进一张无边界键值表。
- [ ] 不创建承担所有杂项能力的公共工具模块。
- [ ] 不保留旧接口、旧字段、双写和隐式兼容逻辑。

## 34. 基座完成验收标准

### 34.1 功能验收

- [ ] 可以从空数据库完成迁移和初始化。
- [ ] 可以安全创建首个管理员。
- [ ] 管理员可以登录、刷新 Token 和退出。
- [ ] 管理员可以管理用户、角色和权限。
- [ ] 服务端能够阻止未认证和未授权访问。
- [ ] 用户禁用、密码重置和强制下线能够正确失效会话。
- [ ] 关键管理操作能够生成准确且脱敏的审计日志。
- [ ] 可以管理部门、岗位、菜单、配置和字典。
- [ ] 可以安全上传、下载和清理本地文件。

### 34.2 架构验收

- [ ] Router 不直接访问数据库。
- [ ] 事务边界位于应用服务。
- [ ] 模块之间没有直接访问对方 ORM 模型或数据表。
- [ ] 认证、用户和权限职责相互分离。
- [ ] 菜单与权限职责相互分离。
- [ ] 部署配置、系统配置和业务配置相互分离。
- [ ] 关键状态不依赖 Python 全局变量。
- [ ] 核心模块不依赖 Redis、消息队列或云存储。
- [ ] 新增业务模块无需修改核心模块内部代码。

### 34.3 质量验收

- [ ] 数据库迁移可从空库完整执行。
- [ ] 核心单元测试和集成测试通过。
- [ ] 类型检查通过。
- [ ] 代码检查通过。
- [ ] 权限与越权测试通过。
- [ ] 日志不存在密码、完整 Token 和密钥。
- [ ] API 文档与实际接口一致。
- [ ] 无循环依赖、重复业务逻辑和无边界公共模块。

### 34.4 部署验收

- [ ] 可以在一台服务器完成完整部署。
- [ ] 可以启动多个 FastAPI Worker。
- [ ] 服务可以优雅关闭和自动重启。
- [ ] 健康检查可以正确反映数据库不可用状态。
- [ ] HTTPS、反向代理和敏感接口限流有效。
- [ ] 数据库和文件备份任务有效。
- [ ] 已通过一次非生产环境恢复演练。

## 35. 每次变更后的架构检查

每次新增或修改代码后，必须检查：

- [ ] 是否增加了不必要的模块耦合。
- [ ] 是否跨越了既定分层或模块边界。
- [ ] 是否引入了隐式状态。
- [ ] 是否复制了已有业务规则。
- [ ] 是否引入了临时 patch、fallback 或兼容逻辑。
- [ ] 是否产生了无法说明用途的抽象。
- [ ] 是否降低了模块的可测试性。
- [ ] 是否破坏事务一致性或权限边界。
- [ ] 是否使数据流和状态流更难推导。
- [ ] 是否增加了部署和运维复杂度。
- [ ] 是否降低了开发者和 AI 的可维护性。

只有在以上检查通过后，变更才应进入基座。
