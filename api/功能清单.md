# FastAPI 后台管理系统 API 基座功能清单

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档用途 | 定义 FastAPI 后台管理系统 API 基座的功能范围、架构边界和交付标准 |
| 目标用户 | 中小型企业后台管理系统及其后续业务项目 |
| 系统形态 | 模块化单体应用 |
| 部署目标 | 单机部署，支持单机多进程 |
| 一致性核心 | PostgreSQL |
| 默认缓存 | 不依赖 Redis |
| 默认文件存储 | 本地文件系统 |
| 兼容策略 | 全新系统，不兼容旧代码、旧接口和旧数据 |
| 技术基线日期 | 2026-07-24 |
| 文档状态 | 架构与验收基线，编码前必须完成评审 |

## 2. 建设目标

本基座作为后续后端项目的统一起点，应满足以下目标：

- [ ] 提供稳定、清晰、可复用的后台管理通用能力。
- [ ] 业务项目可以在不修改核心模块的前提下新增业务模块。
- [ ] 保持模块高内聚、低耦合和单一职责。
- [ ] 明确 API、应用服务、领域规则和基础设施之间的依赖方向。
- [ ] 支持单机环境下的开发、测试、部署、升级、备份和恢复。
- [ ] 不强制依赖 Redis、消息队列、对象存储和 Kubernetes。
- [ ] 为确有需求的基础设施替换保留清晰边界，但不提前实现复杂能力。
- [ ] 代码结构、命名、依赖和状态流应易于开发者及 AI 理解和推导。

## 3. 非建设目标

以下能力不进入基座核心范围：

- [ ] 不建设微服务体系。
- [ ] 不建设服务注册、服务发现和配置中心。
- [ ] 不建设分布式事务。
- [ ] 不建设分布式锁。
- [ ] 不建设强制性的分布式缓存。
- [ ] 不建设消息队列和死信队列平台。
- [ ] 不建设 Kubernetes 专用部署体系。
- [ ] 不内置复杂审批流和通用工作流引擎。
- [ ] 不内置报表设计器、低代码平台和表单设计器。
- [ ] 不内置支付、订单、库存等具体业务功能。
- [ ] 不保留 legacy、deprecated、灰度或 fallback 逻辑。
- [ ] 不为了未来可能发生的需求提前创建无实际用途的抽象层。

## 4. 完成门槛与功能分级

本基座不再使用容易互相覆盖的 P0、P1、P2 作为完成定义。交付采用四个依次累积的完成门槛，后一门槛必须包含前一门槛的全部能力。

| 标识 | 完成门槛 | 可交付结果 |
| --- | --- | --- |
| G1 | Core Ready | 可复用的工程、数据库、API、异常、日志、测试和模块开发基础，不包含后台身份功能 |
| G2 | Security Ready | 在 G1 基础上完成用户、认证、服务端会话、RBAC、安全控制和核心审计 |
| G3 | Admin Ready | 在 G2 基础上完成组织、菜单、系统配置、字典、文件和后台管理通用能力 |
| G4 | Production Ready | 在 G3 基础上完成模板分发、生产部署、反向代理、监控、备份、恢复和演练 |
| EXT | 可选扩展 | 根据具体项目独立启用，不影响 G1 至 G4 的核心验收 |
| 排除 | 非建设目标 | 不进入当前基座 |

门槛规则：

- [ ] 第 6 至 30 章中承载交付能力的三级章节必须明确归属 G1、G2、G3、G4 或 EXT。
- [ ] G1 至 G4 的验收必须依次通过，禁止跳过前置门槛。
- [ ] EXT 未启用时不得产生数据表、路由、配置、依赖或后台进程。
- [ ] 同一能力的实现、测试、部署和运维要求必须归属同一门槛或其后续门槛。
- [ ] “完成基座”特指通过 G4；只通过部分门槛时必须使用对应门槛名称。

## 5. 总体架构

### 5.1 模块化单体

- [ ] 应用以一个代码仓库和一个主要部署单元为基础。
- [ ] 系统按照业务能力划分模块，而不是仅按照技术文件类型划分目录。
- [ ] 用户、认证、授权、组织、菜单、配置、字典、审计、文件等模块彼此独立。
- [ ] 每个模块独立维护路由、应用服务、领域模型、数据模型和测试。
- [ ] 跨模块调用只能通过公开的应用服务或明确的接口完成。
- [ ] 禁止跨模块直接操作对方的数据表、ORM 模型和内部函数。
- [ ] 禁止路由层直接访问数据库。
- [ ] 禁止基础设施层反向依赖 API 层或应用层的具体实现。
- [ ] 禁止通过全局变量保存关键业务状态。
- [ ] 公共代码只承载稳定、无业务归属的能力，禁止形成无边界的 `utils` 模块。

### 5.2 调用流与代码依赖方向

运行时调用流：

```text
HTTP 请求
    ↓
API / Router / Request Schema
    ↓
Application Service / Use Case
    ↓
Domain Policy / Domain Service
    ↓
Application Port
    ↓
Infrastructure Adapter
    ↓
PostgreSQL / File System / External Service
```

编译期代码依赖：

```text
API ───────────────→ Application ───────────────→ Domain
Infrastructure ────→ Application / Domain 定义的 Port
Composition Root ──→ API + Application + Infrastructure
```

依赖规则：

- [ ] Repository、Unit of Work、文件存储和外部服务 Port 由 Application 或 Domain 内层定义。
- [ ] Infrastructure 只实现内层 Port，不得在内层暴露 SQLAlchemy、FastAPI 或具体 SDK 类型。
- [ ] API 和 Infrastructure 可以依赖内层，内层不得依赖外层实现。
- [ ] Composition Root 是唯一允许同时引用接口与具体实现并执行装配的位置。
- [ ] 领域规则不得依赖 FastAPI、ORM、HTTP 或具体存储 SDK。
- [ ] 事务边界由最外层写 Use Case 控制，Router、Repository 和被调用的模块服务不得提交事务。
- [ ] DTO、API Schema、领域对象和 ORM 模型职责分离。
- [ ] 不强制为纯 CRUD 模块创建没有实际领域逻辑的复杂领域模型。

### 5.3 单机部署拓扑

```text
客户端
  ↓
Nginx
  ↓
FastAPI API（一个或多个 Worker）
  ↓
PostgreSQL

可选进程：
- Scheduler：产生定时任务
- Worker：执行持久化后台任务

本地资源：
- 文件存储目录
- 应用日志目录或标准输出
- 数据库及文件备份目录
```

- [ ] API 服务保持无状态，支持在同一台服务器启动多个 Worker。
- [ ] 多 Worker 不共享 Python 进程内状态。
- [ ] 定时调度器不得在每个 API Worker 内重复启动。
- [ ] 关键后台任务不得只存在于进程内存中。

### 5.4 固定技术栈基线（G1）

以下版本是 2026-07-24 评审时完成 CI 验证的初始主版本基线，固定的是经过验证可用的版本线，不承诺等于基线日当日的最新发布。`pyproject.toml` 声明允许范围，`uv.lock` 锁定经过 CI 验证的精确版本；升级主版本或替换组件必须新增 ADR，不允许在业务开发中隐式更换。

| 类别 | 固定选择 |
| --- | --- |
| Python | CPython 3.13.x，开发、CI、生产保持同一小版本系列 |
| Web 框架 | FastAPI 0.139.x，使用 Lifespan 管理应用资源 |
| ASGI Server | Uvicorn，由 `fastapi run` 启动 |
| 数据校验与配置 | Pydantic 2.13.x、pydantic-settings 2.14.x |
| ORM | SQLAlchemy 2.0.x Async ORM，不使用 2.1 预发布版本 |
| PostgreSQL 驱动 | psycopg 3.3.x，SQLAlchemy URL 使用 `postgresql+psycopg` |
| 数据库与迁移 | PostgreSQL 18.x、Alembic 1.18.x |
| 密码哈希 | argon2-cffi 25.x，算法固定为 Argon2id |
| 包与项目管理 | uv 0.11.x，必须提交 `pyproject.toml` 和 `uv.lock` |
| 测试 | pytest 9.x、pytest-asyncio 1.4.x、HTTPX、Testcontainers PostgreSQL |
| 静态检查 | Ruff 0.15.x、mypy 2.3.x strict |
| 架构检查 | import-linter 与项目自定义注册表一致性测试 |
| 依赖安全 | pip-audit，在 CI 中扫描锁定后的完整依赖图 |
| 模板分发 | Copier 9.17.x，模板和派生项目记录模板版本 |
| 生产部署 | Linux 主机、Docker Compose v2、Nginx stable 官方镜像并固定镜像摘要 |

技术规则：

- [ ] 禁止使用 SQLite 替代 PostgreSQL 执行集成测试。
- [ ] 禁止同时引入第二套 ORM、迁移、包管理、lint 或类型检查工具。
- [ ] 运行依赖、开发依赖和模板工具依赖必须分组管理。
- [ ] CI 必须使用 `uv sync --frozen`，禁止在 CI 中临时解析未锁定依赖。
- [ ] 每次依赖升级必须重新执行 G1 至当前最高门槛的全部验收。

### 5.5 模块接入契约（G1）

每个业务模块必须在模块根目录公开唯一的 `ModuleDefinition`，由 Composition Root 中的显式模块清单装配。禁止通过扫描包、导入副作用或命名约定自动发现模块。

`ModuleDefinition` 只声明以下公开信息：

- [ ] 全局唯一且稳定的模块编码。
- [ ] 模块公开的 Application Port。
- [ ] 必需依赖和可选依赖的其他模块编码（允许为空），可选依赖对应的能力在依赖未启用时必须整体关闭。
- [ ] Router 列表和 API Tag。
- [ ] 权限点、错误码、审计动作和受保护资源类型。
- [ ] 幂等初始化器和管理命令。
- [ ] 事务内事件处理器和可选集成事件处理器。
- [ ] Alembic 迁移版本目录。

注册规则：

- [ ] 新增模块只允许新增模块自身代码，并在 Composition Root 的模块清单中增加一项；不得修改核心模块内部实现。
- [ ] Router、权限点、错误码、审计动作、资源类型和命令发生重复时，应用启动与 CI 必须失败并指出冲突来源。
- [ ] 模块依赖只允许指向其他模块的公开 Application Port；必需依赖未启用、依赖构成循环或可选依赖能力未按声明关闭时，应用启动与 CI 必须失败并指出冲突来源。
- [ ] 权限编码固定为小写三段或多段形式，例如 `system:user:read`。
- [ ] 业务错误码固定为 `<MODULE>.<REASON>`，只允许大写字母、数字和下划线，例如 `USER.NOT_FOUND`。
- [ ] 每个模块拥有自己的表、ORM 模型和 Repository Adapter。
- [ ] 跨模块数据库外键默认禁止；确需使用时必须通过 ADR 指定表所有权、删除语义和迁移顺序。
- [ ] Alembic 可以按模块存放版本文件，但所有启用模块必须组成一个全局单头 revision 图。
- [ ] 每个新 revision 的 `down_revision` 必须指向生成时的全局 head；CI 检测到多 head 时失败。
- [ ] 模块初始化器必须可重复执行，只能写入本模块拥有的数据。

### 5.6 跨模块事务决策（G1）

- [ ] `UnitOfWork` Port 定义在 Application 层，Infrastructure 使用一个 `SqlAlchemyUnitOfWork` 实现。
- [ ] 一个最外层写 Use Case 对应一个 Unit of Work 和一个 AsyncSession。
- [ ] Repository Adapter 由 Composition Root 使用当前 Unit of Work 拥有的 AsyncSession 构造。
- [ ] Router 只能获得 Use Case，不得获得 AsyncSession、Repository 或提交接口。
- [ ] 最外层写 Use Case 负责开始、提交或回滚；被调用模块的公开 Application Port 不得提交、回滚或开启隐藏事务。
- [ ] 跨模块强一致操作必须由独立的编排 Use Case 调用各模块公开 Port，并共享同一个 Unit of Work。
- [ ] 禁止通过 ContextVar、线程局部变量或全局变量隐式获取数据库会话。
- [ ] 同一 AsyncSession 不得在并发协程任务间共享；并发任务必须分别创建 Unit of Work。
- [ ] 除明确使用数据库 Savepoint 的用例外，禁止嵌套事务。
- [ ] 事务重试只允许发生在最外层 Use Case，且仅重试已证明幂等的操作。

### 5.7 事件决策（G1）

事件只用于解除已确认的模块依赖，不作为普通函数调用的替代品。

- [ ] Domain Event 是不依赖 FastAPI、ORM 和基础设施的不可变对象。
- [ ] 跨模块事件载荷只允许稳定编码、标量值和资源 ID，不得携带 ORM 模型或可变领域对象。
- [ ] 需要与业务数据强一致的处理器作为事务内事件处理器，在当前 Unit of Work 提交前同步执行。
- [ ] 任一事务内处理器失败时，整个 Use Case 回滚。
- [ ] 事务内处理器不得执行邮件、Webhook、远程 HTTP 调用或其他不可回滚副作用。
- [ ] 可靠的事务后副作用必须使用 PostgreSQL Outbox，并仅在持久化任务扩展启用时注册。
- [ ] 未启用持久化任务扩展时，禁止声称事务后事件可靠送达。
- [ ] 事件及处理器通过 `ModuleDefinition` 显式注册，重复事件编码或处理器编码必须使启动和 CI 失败。
- [ ] 多处理器不得依赖执行顺序；稳定排序只用于保证测试和日志可复现。
- [ ] 成功操作的核心审计必须由 Use Case 显式调用审计 Port，并与业务事务共同提交，不得依赖隐式装饰器或请求中间件猜测业务差异。
- [ ] 失败操作记录到独立安全日志，不得尝试写入已经回滚的业务事务。

### 5.8 请求与用例上下文（G1）

- [ ] Router 将认证结果转换为不可变 `UseCaseContext`，显式传给 Use Case。
- [ ] `UseCaseContext` 只包含 Request ID、Actor ID、Session ID、当前时间和已验证的安全元数据。
- [ ] 领域规则通过显式 Clock Port 获取时间，通过显式 ID Generator Port 获取标识。
- [ ] ContextVar 只允许用于日志关联，不得作为业务授权、事务或领域状态的数据源。

## 6. 应用启动与系统基础能力

### 6.1 应用生命周期（G1）

- [ ] 提供统一的应用创建入口。
- [ ] 使用 FastAPI Lifespan 提供启动和关闭生命周期管理，不使用已废弃的事件式写法。
- [ ] 启动时校验必需配置。
- [ ] 启动时初始化数据库连接池；数据库暂时不可用只影响就绪状态，不得使存活检查失效。
- [ ] 关闭时释放数据库连接池和其他资源。
- [ ] 禁止在模块导入阶段执行数据库访问等隐式副作用。
- [ ] 支持开发、测试和生产环境配置。
- [ ] 提供应用名称、版本、环境等运行信息。

### 6.2 健康检查（G1）

- [ ] `GET /health/live` 只验证进程事件循环可响应，数据库不可用时仍返回 HTTP 200。
- [ ] `GET /health/ready` 验证数据库连接和当前 Alembic revision 与应用要求一致；发布按 26.1 停机切换，运行中的应用不要求兼容其他版本的 revision。
- [ ] 就绪条件任一失败时返回 HTTP 503 和稳定错误码，恢复后无需重启进程即可重新就绪。
- [ ] 健康检查返回内容不泄露敏感配置。
- [ ] 允许反向代理和进程管理器使用健康检查判断服务状态。

### 6.3 时间与时区（G1）

- [ ] 数据库时间字段使用 PostgreSQL `timestamptz`，写入和比较统一使用 UTC。
- [ ] API 时间字段统一使用带时区的 ISO 8601 格式。
- [ ] 展示时区由调用端或明确的系统配置决定。
- [ ] 禁止使用无时区语义的时间参与关键业务计算。

## 7. 配置管理

### 7.1 部署配置（G1）

- [ ] 通过环境变量或受控配置文件加载部署配置。
- [ ] 提供开发环境配置示例，但不提交真实密钥。
- [ ] 必需配置缺失时快速失败并给出明确错误。
- [ ] 配置项具有类型校验。
- [ ] 配置项具有清晰的名称、默认值和用途说明。
- [ ] 数据库地址、密钥、文件目录等部署配置不得存入系统配置表。
- [ ] 生产环境禁止使用不安全的默认密钥。

### 7.2 配置分类（G1）

- [ ] 明确区分部署配置、系统配置和业务配置。
- [ ] 部署配置由运维环境管理。
- [ ] 系统配置由后台管理员管理。
- [ ] 业务配置归属于具体业务模块。
- [ ] 禁止把三类配置混合到同一个无边界配置模块中。

## 8. 数据库基础设施

### 8.1 PostgreSQL 数据访问（G1）

- [ ] 提供数据库连接池。
- [ ] 支持异步数据访问。
- [ ] 通过 Unit of Work 提供用例级 AsyncSession，不向 Router 暴露数据库会话。
- [ ] 提供符合 5.6 的统一事务管理机制。
- [ ] 正确处理提交、回滚和连接释放。
- [ ] 数据库异常转换为稳定的应用异常。
- [ ] 禁止在 Unit of Work 生命周期之外复用数据库会话。
- [ ] 禁止在 `asyncio.gather` 等并发任务之间共享同一个 AsyncSession。
- [ ] 避免 N+1 查询。
- [ ] 关键列表查询具有明确索引设计。

### 8.2 数据库迁移（G1）

- [ ] 固定使用 Alembic 管理结构变更。
- [ ] 所有表结构变更必须通过迁移文件交付。
- [ ] 迁移文件纳入版本控制。
- [ ] 部署前可以独立执行迁移。
- [ ] 迁移失败时不得继续启动新版本应用。
- [ ] 提供全新数据库初始化流程。
- [ ] 所有已启用模块共同组成唯一 Alembic head，禁止长期保留多 head。
- [ ] CI 必须从空 PostgreSQL 18 数据库执行 `alembic upgrade head`。
- [ ] 数据迁移必须明确批量大小、锁影响、失败恢复和是否可重复执行。
- [ ] 不要求提供自动 downgrade；不可逆迁移必须在文件中说明恢复方式。
- [ ] 不提供旧系统数据兼容迁移和双写逻辑。

### 8.3 数据建模规范（G1）

- [ ] 每张业务表具有明确主键。
- [ ] 表名、字段名、索引名和约束名遵循统一规范。
- [ ] 外键关系是否使用数据库约束必须形成统一决策。
- [ ] 唯一性规则优先由数据库唯一约束保证。
- [ ] 金额、比例和精度数据禁止使用浮点类型。
- [ ] 枚举值具有稳定编码。
- [ ] 敏感字段明确加密、哈希或脱敏策略。
- [ ] 不把软删除设计成所有表的强制基类能力。
- [ ] 是否允许软删除由具体模块的数据生命周期决定。
- [ ] 审计日志等不可变数据不得通过通用 CRUD 随意修改。

### 8.4 并发与幂等（G1）

- [ ] 关键并发更新使用数据库事务、行锁或乐观锁处理。
- [ ] 幂等性优先使用业务唯一键和数据库唯一约束实现。
- [ ] 不依赖进程内锁保证跨 Worker 正确性。
- [ ] 不引入分布式锁。
- [ ] 冲突错误具有明确的业务错误码。

### 8.5 初始化机制（G1）

- [ ] 初始化框架由 G1 提供，各模块通过 `ModuleDefinition` 注册本模块初始化器。
- [ ] 初始化器使用稳定自然键或稳定编码执行幂等 upsert，不得按显示名称判断重复。
- [ ] G2 的身份模块负责首个管理员和基础权限点初始化。
- [ ] G3 的菜单与字典模块分别负责基础菜单和系统字典初始化。
- [ ] 初始化过程可重复执行且不会创建重复数据。
- [ ] 初始化密码不得硬编码、写入命令历史或输出到日志。
- [ ] 开发演示数据和生产初始化数据使用不同命令与数据源。

## 9. API 通用规范

### 9.1 路由与版本（G1）

- [ ] API 使用统一前缀。
- [ ] API 具有明确版本，例如 `/api/v1`。
- [ ] 路由按业务模块分组。
- [ ] 路由命名与 HTTP 方法语义一致。
- [ ] 禁止通过一个巨型路由文件承载全部接口。
- [ ] 不为不存在的旧客户端保留兼容路由。

### 9.2 请求模型（G1）

- [ ] 请求参数使用明确的 Schema 校验。
- [ ] 创建、更新、查询和响应模型按职责区分。
- [ ] 更新接口明确区分全量更新和部分更新。
- [ ] 字符串长度、数值范围、格式和枚举具有约束。
- [ ] 未知字段的处理策略保持统一。
- [ ] 创建、全量更新和部分更新请求统一拒绝未知字段，Pydantic 模型使用 `extra="forbid"`。
- [ ] 文件上传具有大小、类型和数量限制。

### 9.3 响应模型（G1）

- [ ] 普通成功响应直接返回资源 Schema，不使用 `{code, message, data}` 成功信封。
- [ ] 创建成功返回 HTTP 201，并在适用时返回 `Location`。
- [ ] 无响应体的删除成功返回 HTTP 204。
- [ ] 文件和流式响应不套 JSON 信封。
- [ ] 错误响应固定采用 RFC 9457 `application/problem+json`。
- [ ] 错误模型固定包含 `type`、`title`、`status`、`detail`、`instance`、`code` 和 `request_id`；业务错误的 `type` 固定为 `urn:` 加应用标识加 `problem` 加小写错误码，例如 `urn:apex:problem:user.not_found`，无业务错误码的框架级错误使用 `about:blank`。
- [ ] 字段校验错误额外包含 `errors` 数组；数组元素固定包含 `field`、`reason` 和 `message`。
- [ ] `detail` 和 `message` 只供展示，客户端业务判断只能使用稳定 `code`。
- [ ] 响应结构不得把业务错误包装为 HTTP 200。
- [ ] 响应字段具有稳定命名规范。
- [ ] JSON 字段统一使用 `snake_case`，时间统一为带时区 ISO 8601 字符串。
- [ ] 敏感字段不得进入响应模型。
- [ ] API 文档准确展示实际响应结构。

### 9.4 分页、排序和筛选（G1）

- [ ] 页码分页参数固定为 `page` 和 `page_size`，默认值分别为 1 和 20。
- [ ] `page` 最小值为 1，`page_size` 范围为 1 至 100。
- [ ] 页码分页响应固定为 `{items, total, page, page_size, pages}`。
- [ ] 排序参数固定为 `sort`，使用逗号分隔字段，前缀 `-` 表示降序，例如 `-created_at,name`。
- [ ] 排序字段使用每个查询显式声明的白名单，不在白名单内返回参数错误。
- [ ] 筛选字段由具体模块显式声明。
- [ ] 禁止将客户端输入直接拼接为 SQL。
- [ ] 游标分页必须使用独立响应模型，禁止与页码分页参数混用。
- [ ] `total` 查询超出具体模块性能预算时，该模块必须通过 ADR 改用游标分页。

### 9.5 请求上下文（G1）

- [ ] 每个请求生成或接收唯一 Request ID。
- [ ] 请求上下文按 5.8 转换为不可变 `UseCaseContext`。
- [ ] 业务上下文显式传递，不依赖难以推导的隐式全局状态。
- [ ] Request ID 写入响应头和结构化日志。

### 9.6 OpenAPI 文档（G1）

- [ ] 接口按模块分组。
- [ ] 每个接口具有摘要和必要说明。
- [ ] 请求、响应和错误模型完整。
- [ ] 认证方式正确集成到 OpenAPI。
- [ ] 每个 Operation ID 全局唯一且稳定，CI 对 OpenAPI JSON 执行快照比较。
- [ ] 生产环境可以关闭文档或限制访问。
- [ ] 文档不暴露内部密钥、数据库信息和堆栈详情。

## 12. 认证与会话

### 12.1 账号密码认证（G2）

- [ ] 用户名和密码登录。
- [ ] 密码固定使用 Argon2id 和 argon2-cffi。
- [ ] Argon2id 参数固定为 `memory_cost=65536` KiB、`time_cost=3`、`parallelism=1`，变更参数必须通过安全 ADR 和性能测试。
- [ ] 登录成功时使用 `check_needs_rehash` 判断并在同一事务中升级旧参数哈希。
- [ ] 登录前检查用户状态。
- [ ] 登录成功创建服务端会话。
- [ ] 登录失败记录安全事件。
- [ ] G2 固定使用不透明随机 Bearer Access Token，不使用 JWT。
- [ ] Access Token 使用密码学安全随机数生成器产生至少 256 bit 熵，默认有效期 15 分钟。
- [ ] Access Token 仅在登录或刷新响应体中返回一次，前端只允许保存在内存中。
- [ ] Refresh Token 使用至少 256 bit 熵，只通过 HttpOnly Cookie 传递，不进入 JSON 响应。
- [ ] 登录和刷新响应必须设置 `Cache-Control: no-store`。

### 12.2 Token 存储与刷新（G2）

- [ ] 使用 Refresh Token 获取新的 Access Token。
- [ ] 数据库只保存 Access Token 和 Refresh Token 的 HMAC-SHA-256 摘要，不保存明文 Token。
- [ ] Access Token 和 Refresh Token 使用两个独立的部署密钥计算摘要，密钥不得存入数据库。
- [ ] 两个 Token 摘要密钥分别具有至少 256 bit 熵，配置缺失、相同或长度不足时应用启动失败。
- [ ] Refresh Token 每次使用都必须轮换，新旧状态变更在同一数据库事务中完成。
- [ ] 每个 Refresh Token 记录所属 Session、Token Family、前驱、创建时间、使用时间、过期时间和吊销原因。
- [ ] 刷新事务对当前 Token Family 加行锁；同一 Refresh Token 并发请求只允许一个成功。
- [ ] 已使用 Refresh Token 再次出现时视为重放，立即吊销整个 Session 和 Token Family。
- [ ] 前端必须对刷新请求实施 single-flight；不提供降低重放检测强度的并发宽限窗口。
- [ ] 刷新时检查用户和会话状态。
- [ ] 会话被吊销后不可继续刷新。
- [ ] 刷新成功时替换当前 Access Token 摘要，旧 Access Token 立即失效；同一会话同时最多一个有效 Access Token，多个浏览器标签页必须由前端通过跨标签页协调共享刷新结果，不得各自独立刷新。

### 12.3 会话管理与在线校验（G2）

- [ ] 会话信息持久化到 PostgreSQL。
- [ ] 每个受保护请求都使用 Access Token 摘要查询 PostgreSQL，并校验用户启用、会话有效、Token 有效、空闲过期和绝对过期。
- [ ] 权限不写入 Token；每个受保护请求基于数据库当前角色和权限关系完成授权。
- [ ] 用户禁用、角色禁用、权限移除或会话吊销提交后，后续请求立即按新状态拒绝。
- [ ] 用户可以查看自己的活动会话。
- [ ] 用户可以退出当前会话。
- [ ] 用户可以退出其他会话。
- [ ] 管理员可以强制用户下线。
- [ ] 用户被禁用后，其有效会话全部失效。
- [ ] 管理员重置密码后吊销该用户全部会话；用户主动修改密码时保留当前会话并吊销其他会话。
- [ ] 会话记录设备、IP、User-Agent、创建时间和最近活动时间。
- [ ] 会话默认空闲过期时间为 30 分钟，默认绝对过期时间为 12 小时。
- [ ] Refresh Token Cookie 和数据库 Token 的过期时间不得晚于会话绝对过期时间。
- [ ] 最近活动时间最多每 5 分钟条件更新一次，禁止每个请求无条件写库。

### 12.4 浏览器传递与登录安全（G2）

- [ ] Refresh Token Cookie 固定命名为 `__Host-apex_refresh`，设置 `Secure`、`HttpOnly`、`SameSite=Strict`、`Path=/`，不得设置 `Domain`。
- [ ] 本地开发统一通过 `localhost` 访问，利用主流浏览器对 `localhost` 的可信来源规则在 HTTP 下使用 `Secure` Cookie；禁止使用 IP 地址或自定义域名绕过，不提供关闭 `Secure` 的配置开关。
- [ ] Refresh、Logout 等读取 Cookie 的状态变更接口必须校验 `Origin` 是否精确匹配部署配置白名单。
- [ ] G2 默认只支持前端与 API 同站部署；跨站部署必须新增安全 ADR 和对应 CSRF 集成测试。
- [ ] 除 Refresh Token Cookie 外，业务接口不得接受 Cookie 作为认证凭证。
- [ ] Logout 必须吊销服务端会话并使用相同 Cookie 属性删除客户端 Cookie。
- [ ] 记录连续登录失败。
- [ ] 登录失败状态持久化到 PostgreSQL，以规范化账号标识和可信客户端 IP 作为独立维度统计。
- [ ] 同一账号连续失败 5 次后限制 15 分钟；成功登录后清理该账号失败状态。
- [ ] 同一可信客户端 IP 连续失败 20 次后限制 15 分钟，到期自动解除；该维度只累计失败，成功登录不清理，任一维度触发限制时的响应与账号密码错误响应保持一致。
- [ ] 防止通过错误响应枚举有效用户。
- [ ] 用户不存在时执行固定的 Argon2id 虚拟哈希校验，降低响应时间差导致的账号枚举风险。
- [ ] G4 由 Nginx 对登录和刷新接口执行入口频率限制。
- [ ] 登录日志记录成功、失败和失败原因分类。
- [ ] 不在日志中记录明文密码、完整 Token；如启用验证码扩展，同样不得记录验证码内容。

- [ ] 文件元数据持久化到 PostgreSQL。
- [ ] 文件元数据包含原始名称、存储名称、大小、类型、哈希、上传者和时间。
- [ ] 临时目录与正式目录位于同一文件系统，确保最终移动可以使用原子 rename。
- [ ] 存储目录不得位于 Web Root，应用不得跟随存储目录中的符号链接。

### 19.2 上传与下载（G3）

- [ ] 限制单文件大小。
- [ ] 限制单次上传数量。
- [ ] 上传必须分块流式写入并在读取过程中累计大小和 SHA-256，禁止一次性读取整个文件到内存。
- [ ] 使用白名单校验允许的文件类型。
- [ ] 同时检查扩展名、声明类型和必要的文件内容特征。
- [ ] 支持授权下载私有文件。
- [ ] 下载接口防止未授权枚举文件。
- [ ] 响应头安全处理原始文件名。
- [ ] 上传和删除行为记录审计日志。

### 19.3 文件状态机（G3）

文件元数据状态固定为：

```text
PENDING → READY → DELETING → DELETED
   │         │
   └─────────┴────→ FAILED
```

- [ ] API 只允许下载 `READY` 文件。
- [ ] 上传首先流式写入服务器生成名称的临时文件，校验完成后创建 `PENDING` 元数据。
- [ ] `PENDING` 元数据提交后，使用原子 rename 将临时文件移动到最终路径，再在新事务中更新为 `READY`。
- [ ] 请求失败时尽力清理临时文件；进程崩溃后的残留由一致性命令恢复。
- [ ] `PENDING` 存在最终文件且哈希一致时，一致性命令将其推进为 `READY`。
- [ ] `PENDING` 不存在最终文件且超过 1 小时时，一致性命令标记为 `FAILED`。
- [ ] 临时目录中超过 24 小时且没有活动上传记录的文件必须清理。
- [ ] 删除前必须在事务中确认没有活动业务引用并更新为 `DELETING`，并记录进入 `DELETING` 的时间。
- [ ] `DELETING` 文件的物理删除至少延迟 7 天，以满足 27.2 的备份窗口要求；到期物理删除成功后更新为 `DELETED`，物理删除失败时保持 `DELETING` 并允许幂等重试。
- [ ] `READY` 元数据缺少物理文件时标记为 `FAILED` 并产生高优先级运维日志，不得返回空内容。
- [ ] 备份只包含 `READY` 文件和对应元数据；`PENDING`、`FAILED`、`DELETING` 不视为有效业务文件。

### 19.4 业务引用与授权边界（G3）

- [ ] 文件模块拥有文件元数据和文件引用记录，业务模块只保存或传递稳定 File ID。
- [ ] 业务模块通过文件模块公开 Port 执行 `retain` 和 `release`，不得直接写文件引用表。
- [ ] 文件引用必须包含业务模块编码、资源类型和资源 ID，并具有防重复唯一约束。
- [ ] 文件模块不反向查询业务模块数据表。
- [ ] 业务资源附件的下载必须先由业务模块校验资源访问权限，再调用文件读取 Port。
- [ ] 通用文件管理接口只允许上传者管理临时文件或拥有文件管理权限的管理员访问，不代替业务资源授权。
- [ ] 业务事务回滚时，文件引用必须同时回滚；未被引用的正式文件由受控清理命令按保留期清理，保留期不短于 19.3 的 7 天物理删除延迟。

### 19.5 存储扩展边界（EXT）

- [ ] 业务模块依赖文件存储接口，而不是直接操作磁盘。
- [ ] 仅在项目有明确需求时增加 S3、OSS 等对象存储实现。

## 35. 每次变更后的架构检查

每次新增或修改代码后，必须检查：

- [ ] 是否增加了不必要的模块耦合。
- [ ] 是否跨越了既定分层或模块边界。
- [ ] 是否引入了隐式状态。
- [ ] 是否复制了已有业务规则。
- [ ] 是否引入了临时 patch、fallback 或兼容逻辑。
- [ ] 是否产生了无法说明用途的抽象。
- [ ] 是否降低了模块的可测试性。
- [ ] 是否破坏事务一致性或权限边界。
- [ ] 是否使数据流和状态流更难推导。
- [ ] 是否增加了部署和运维复杂度。
- [ ] 是否降低了开发者和 AI 的可维护性。

只有在以上检查通过后，变更才应进入基座。
